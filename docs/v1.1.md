# HoloCore v1.1 — Control Centre and reliability foundation

**Status:** Released as v1.1.0. This document records delivered behavior and follow-up requirements; the latter are not included in v1.1.0.

## Goal

Give users one desktop Control Centre for checking HoloCore and its AI client connections, reviewing operational quality, controlling background work, and recovering local data. Strengthen the API and SQLite storage behavior that these workflows depend on.

## Progress snapshot

v1.1.0 ships the native desktop Control Centre and shared local Python service adapter, project and knowledge browsing, AI connection health checks, Memories and Code Map views, Home backup and restore, scheduled backups, the Obsidian Board plugin, and SQLite reliability improvements. This is not a network API.

The installer adds a **HoloCore Control Centre** Start menu shortcut that opens the windowed Setup executable with `--desktop`, so no console window appears; uninstall removes it with the other shortcuts. Launched without arguments, the Control Centre uses the selected HoloCore Home and opens the registered project that contains the current folder, otherwise the one with the most recent AI activity. It browses project knowledge, the Second Brain project's curated notes, and the whole Home, plus memories (with an optional filter for short or mechanical fragments) and the most connected code in the Code Map, all read-only.

The AI Connections tab now shows configuration, connection test, and last capture as separate values. **Test** starts the exact HoloCore command the client is configured to run and performs an MCP `initialize` and `tools/list` handshake without changing client configuration. Last capture is the latest activity-ledger event recorded from that client for the selected project, read-only; a missing value is shown as "No capture recorded".

**Backup, restore, and portability** (Control Centre → Storage & Backups, or `holocore backup create|check|restore|schedule|unschedule|status`):

- A backup is one `.zip` of everything HoloCore cannot rebuild: the project registry, Knowledge, original chat transcripts, a consistent SQLite snapshot of the Memories database (committed WAL data included), and each project's `world.json`, `Sources`, `Inbox`, and `Runtime`. Code maps, the generated Obsidian vault view, Console exports, AI connection files, `.bak` files, SQLite journal files, and junction aliases are left out. A `manifest.json` records the HoloCore, layout, and schema versions, the source Home, per-category totals, and a SHA-256 for every file; a `README.txt` explains how to restore it. The same file is the portable export.
- **Check** verifies every checksum and reports the backup's date, version, contents, compatibility problems (newer format or schema, different folder layout, unsafe paths), projects that would leave the registry, and memories newer than the backup — without changing anything.
- **Restore** refuses an invalid backup, saves a `pre-restore` safety backup (newest 3 kept in `<Home>\Restore Safety Backups`), stages and validates the files, swaps them in, and replaces the database contents in one SQLite transaction so running AI tools need not be closed. Any failure puts every moved folder and the previous database back. Restoring into a Home at a different path rewrites the saved Home paths in `worlds.json` and each `world.json`.
- **Scheduled backups** create a Windows Task Scheduler task (`HoloCore Backup`, daily or weekly; weekly with 4 kept is the default) that runs the windowed Setup with `--backup-scheduled`, so no console appears. There is no default folder; nothing runs until one is chosen. Each run prunes older scheduled backups and records its outcome — time, size, or error — which the Storage page shows as **Last scheduled backup**.
- Measured on a real Home (≈128 MB across 3,971 files): a backup takes about 13 s and produces a 75 MB zip; a full checksum check takes about 1 s.

**Memories database reliability and scale:**

- Each HoloCore process keeps one database connection per thread instead of opening one for every operation. A nested operation gets its own connection, so it can never commit an outer transaction early, and a connection that fails is closed rather than reused.
- When another program holds the write lock past SQLite's 30-second busy wait, the error names the database and says what to do, instead of a bare `database is locked`. It is still an `sqlite3.OperationalError`, so existing handlers catch it.
- After a chat capture commits, a passive WAL checkpoint folds committed changes into the database file without waiting on other programs. Its result is recorded in the capture diagnostics; when a reader blocks it, the changes stay committed in the WAL and a later checkpoint folds them in.
- Merging a legacy database commits every 500 rows. Every merge write skips rows that were already merged, so an interrupted merge finishes when it runs again and gives the same result as an uninterrupted one.
- Tests cover a writer process killed mid-write (every reported memory survives, `integrity_check` passes, the database keeps working), a held write lock, a checkpoint blocked by a reader, an interrupted merge, and raw chat audits staying byte-identical through reprocessing and consolidation.

Measured on a Windows 11 laptop. Concurrent writers: 1, 4, and 8 processes each saving 150 memories plus activity events took 0.3, 1.3, and 2.4 s with no failures, against 3.1, 11.7, and 20.0 s before connection reuse. The opt-in scale test (`HOLOCORE_SCALE_TEST=1 pytest tests/test_sqlite_scale.py -s`) puts every memory in one project, the worst case for search:

| Memories | Database | Save one memory | Search | Board | Integrity check | Backup |
|---|---|---|---|---|---|---|
| 1,200 | 1.1 MB | 0.9 ms | 0.003 s | 0.04 s | 0.003 s | 0.02 s |
| 20,200 | 16 MB | 0.9 ms | 0.07 s | 0.20 s | 0.15 s | 0.16 s |
| 200,200 | 162 MB | 1.1 ms | 0.65 s | 0.45 s | 5.0 s | 3.8 s |

Saving now takes the same time at every size. Before this work it took 9.3 ms at 20,200 memories and 145 ms at 200,200, because the duplicate check did not match the unique index and read every memory in the project. Search reads every memory in the project, so its time grows with the project's size. For scale, the HoloCore Home this was developed against holds about 19,000 memories, with at most about 3,500 in one project.

The shipped release does not include chat deletion, incremental processing with pause/resume, or a performance and retrieval-quality dashboard. These remain planned requirements for v1.2, along with expanded scale and recovery coverage. The acceptance requirements below describe that follow-up scope, not shipped v1.1.0 behavior.

## Follow-up requirements (not in v1.1.0)

### Desktop Control Centre and connection health

- Integrate first-run setup and the ongoing Control Centre into one desktop application and one window. After first-run setup, the same app opens to the Control Centre; users can return to Setup from inside it.
- Bring project, AI connection, capture, processing, and recovery controls into the ongoing Control Centre.
- Provide a searchable conversation-history view with source/client and capture time, and let users delete an individual captured conversation when it is no longer needed.
- Before deletion, show the related derived memories and promoted Knowledge entries. Let the user choose whether to keep or remove those derived items; never delete unrelated project files or source material implicitly.
- Show each supported AI connection's configured state, current connection state, and timestamp of its last successful capture as separate values.
- Provide a user-invoked **Test** action and show its result, time, and actionable failure detail. Testing must not silently rewrite client configuration.
- Distinguish unavailable, disconnected, not configured, and connected states. A successful connection test must not be presented as proof that capture is working; capture recency is reported separately.

### Incremental processing and controls

- Process only new or changed eligible inputs when prior work can be reused safely; expose enough status to tell what is queued, running, completed, or failed.
- Reuse cached results only when their inputs and relevant processing version still match. Changed inputs or incompatible versions invalidate the affected cache entries.
- Expose busy and pause/resume behavior for supported background processing. Pause prevents new work from starting and reaches a safe checkpoint for active work; resume continues without duplicate results or lost inputs.

### Performance and quality dashboard

- Report measured latency, token usage where available, data/index freshness, and retrieval relevance with clear definitions, time windows, and source timestamps.
- Mark unavailable or partial measurements explicitly; do not substitute estimates for measured values or present missing data as zero.
- Let users inspect enough per-operation or per-sample evidence to understand how aggregate values were produced, without exposing prompts, full payloads, credentials, or secrets.

### Backup, restore, and portability

- Let users create a backup on demand and configure scheduled local backups, with last-run status, completion time, and failure detail.
- Restore preview identifies the backup timestamp and version, included data categories, destination, and conflicts or compatibility issues before any replacement occurs.
- Restore is all-or-nothing from the user's perspective: preserve the pre-restore state for recovery, validate the restored data, and report success or a recoverable failure.
- Produce a portable export that can be moved to another HoloCore installation and document what it contains and how it can be restored.
- Backups and exports use a consistent SQLite snapshot and include the data needed to preserve referential integrity; do not copy a live database in a way that can omit committed data.

### Local service boundary and SQLite reliability

- Keep raw transcript storage separate from derived memories, summaries, and indexes; derived-data rebuilds must not mutate or discard the original transcript records.
- Bound write transactions so large captures and indexing batches do not hold database locks indefinitely. Checkpoint WAL data at documented safe points and report checkpoint failures.
- Handle lock contention with bounded retries and clear errors; after interruption, recover or report the database state without silently dropping committed inputs.
- Run SQLite integrity validation at the defined backup/restore and recovery boundaries, and reject or isolate invalid restore candidates before they replace live data.
- Keep backup and restore snapshots internally consistent across related tables, including schema/version metadata.
- Exercise representative small, medium, and large data sets, interrupted writes, lock contention, checkpointing, backup/restore, and integrity failure paths. Record supported scale assumptions and measured limits.

## Acceptance criteria

1. From the Control Centre, a user can see each supported connection's configured state, connection state, and last successful capture time, then invoke **Test** and read a timestamped result. Tests cover not-configured, disconnected, failed, and successful cases.
2. Capture health is shown independently of connection health. A connection can pass **Test** while stale capture remains visibly stale, and a missing capture timestamp is not reported as a successful capture.
3. A user can find captured conversations, inspect their source and date, preview what deletion affects, and delete a selected conversation. The operation removes the raw captured transcript and only the derived memories/Knowledge the user selected; unrelated project data remains intact.
4. Given unchanged inputs, a second incremental run reuses valid results and avoids reprocessing them. Given a changed input or processing-version change, only affected invalid cache entries are recomputed and no stale result is shown as current.
5. Pausing while work is queued or running stops new work and reaches a documented safe point; resuming completes pending work once, with no lost inputs or duplicate derived records.
6. The dashboard displays latency, token use, freshness, and relevance with definitions, time bounds, provenance, and timestamps. Missing or partial data is labeled and cannot be mistaken for a measured zero.
7. A scheduled backup can be configured and its latest outcome inspected. A backup can be previewed, exported, moved to another compatible installation, and restored with its data categories and compatibility checks visible before restore.
8. An interrupted or invalid restore leaves the current data recoverable. A successful restore passes integrity validation and includes a consistent snapshot of related data and schema metadata.
9. Raw transcript records remain intact through derived-memory rebuilds, interruption recovery, and restore. Bounded writes, WAL checkpointing, lock recovery, and integrity checks behave as documented under representative scale and failure tests.
10. Local service and storage changes preserve documented v1 compatibility contracts or include explicit migrations and compatibility coverage before release. No network API is implied by the shared service adapter.

## Out of scope for v1.1

- The Obsidian plugin and interactive duplicate/conflict/staleness review are targeted for v1.2.
- Task context packs for bug investigation, continuing work, and code explanation are targeted for v1.2.
- The selected-page Notion connector and synchronization, agent handoffs for decisions/files/tests/blockers/next steps, and cross-project sharing are targeted for v1.3.

Incremental efficiency and measurement work are planned for v1.2 and v1.3 based on further scale evidence.
