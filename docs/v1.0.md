# HoloCore v1.0.0 release candidate

HoloCore v1.0 consolidates the semantic Code Map, complete Memories workspace, guided research and architecture workflows, native Windows setup, recoverable upgrades, and plain-language integrations into one compatibility-frozen release line.

## User-facing release

- One native four-step Windows setup application selects HoloCore Home, the first project, supported AI clients, optional Code Map generation, update checks, and an installed Ollama model.
- Knowledge, Code Map, Memories, Chat History, and Agent Activity use plain product language throughout current interfaces.
- Claude Code, Codex, Cursor, Gemini CLI, and OpenCode share one generated connection bundle and retain unrelated user configuration.
- Every registered project can be reconciled through `holocore sync-all --regenerate`.
- Older `animus*` and `atlas*` imports and commands remain compatibility aliases while new integrations use `memory-*` and `code-map-*` names.

## Data and recovery guarantees

- Memories schema upgrades use explicit numbered migrations, a pre-migration SQLite backup, an integrity check, transaction rollback, and a migration journal.
- First-run setup records an atomic operation journal and resumes completed idempotent steps after interruption.
- The Windows installer retains the previous executable pair, supports explicit rollback, and preserves HoloCore Home during uninstall.
- The published CLI, MCP, storage, and installer compatibility contracts are documented in [v1-contracts.md](v1-contracts.md).

## Release supply chain

- Pull requests and `main` pushes run the source suite and build both Windows artifacts.
- Tagged builds accept only the stable package tag or a numbered `-rc.N` tag and require Authenticode signing credentials.
- The installer fails closed on missing manifests, checksum mismatches, invalid signatures, or signer mismatches.
- Every tag produces SHA-256 checksums, a schema-v2 immutable release manifest, a reproducible CycloneDX SBOM, and GitHub build-provenance attestations.
- The exact signed artifacts execute setup/status smoke tests and an install, upgrade, rollback, uninstall, and data-preservation lifecycle before publication.

## Promotion rule

Publish `v1.0.0-rc.1` and `v1.0.0-rc.2` as signed GitHub prereleases. The final `v1.0.0` tag may be published only after both immutable release-candidate lifecycle runs complete with no open P0 or P1 defects. An unsigned local build is a test artifact, never the stable release.
